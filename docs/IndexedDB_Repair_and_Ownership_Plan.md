## Original problem (repaired on Mac)

On the user's 2018 MacBook Pro, Chrome serving Memora through VS Code Live Server, opening Whisper Models did not show Model Registry. The supplied Console trace confirms `NotFoundError` at `storage.js:409` when `listModelRegistryRecords()` requests a transaction on `modelRegistry`. That confirms the required store is absent in the database opened by this path. Inspect the live database version and full store/index inventory before repair; the prior architecture plan records a version-4 missing-store observation, but the current Console trace alone does not establish version.

Settings awaits registry loading before creating its heading/controls and calls that asynchronous renderer without handling its rejection. This explains the absent section and uncaught promise error. It does not prove the cause of the earlier intermittent return to Transcription/favicon activity. Live Server reloads are a possible separate explanation; that behavior is currently stable and unconfirmed.

Code inspection finds different database owners: `storage.js` opens Memora version 4 and creates transcripts, semantic stores/indexes, and modelRegistry; `semantic.js` also opens version 4 but does not create modelRegistry. `storageManager.js` contains versionless opens for reporting/operations. Existing version-4 opens do not trigger an upgrade merely because a store is missing. Competing upgrade definitions provide a mechanism for incomplete schemas, but the exact historical creation order on this Mac is not proven.

## Ordered checkpoints

Current checkpoint: all openers use the version-5 owner; isolated tests passed (12 schema groups, six integration groups), and the user confirmed Mac registry, Search persistence, Tiny transcription/self-test, and all four stores. Commit `35d69cd` is awaiting GitHub Pages/iPhone verification. The sequence below records the implementation approach; it is not a list of wholly unstarted tasks. See [audit and repair design](IndexedDB_Audit_and_Repair_Design.md).

1. **Audit before code changes.** Search the entire repository for database opens, upgrades, transactions, deletion/reset paths, and connection lifecycles. Inventory every store, key path, index, caller, and preservation/recovery requirement. Distinguish IndexedDB from Cache Storage and browser model caches. Record the live origin, database version, store/index names, and baseline counts without dumping transcript/embedding contents. Audit reporting reads for unnecessary bulk loading. Deliver a reviewed dependency map and exact upgrade design.
2. **Implement one database owner.** Choose a small module such as `database.js` after the audit. It alone owns opening Memora, schema definitions, validation, upgrades, and connection handling. Serialize concurrent initialization. Define whether consumers borrow a connection or obtain short-lived connections before migrating callers; do not leave callers closing a shared connection unexpectedly. Keep the new owner unused until its isolated checks pass.
3. **Migrate all opening paths and activate the repair together.** Consumers can be prepared incrementally, but no production opener should activate a new schema version while older openers still request version 4. Those opens would fail with VersionError. Choose the next version only after confirming deployed versions. Use one coordinated, reviewable integration change for the version transition and all active openers, preserving existing public data-access APIs where practical.
4. **Upgrade without deleting data.** Create missing stores/indexes through the version-change transaction. Leave existing records and validation evidence intact. Inspect existing key paths/index definitions and define what happens for incompatible structures; do not silently drop/recreate them. Define whether missing registry definitions are populated on demand or during initialization. Transaction abort must leave the old database intact. Do not use database deletion or record rebuild as schema repair.
5. **Validate and report failures.** Check the required schema after opening. Surface missing/incompatible schema, permission/storage failures, blocked upgrades, and version mismatch distinctly. Close on versionchange, handle blocked/error/abort paths, and clear failed initialization state so retry behavior is explicit. Avoid automatic repeated version bumps or destructive fallback. Settings should render a registry heading/loading/error state independently of record loading, catch async failures, and leave runtime diagnostics usable where possible. Treat that UI/error-boundary change as its own testable checkpoint.
6. **Verify preservation and recovery.** Use isolated test databases/origins first: fresh database; healthy existing database; incomplete version-4 database without modelRegistry; existing registry/evidence; concurrent consumers; multiple tabs blocking an upgrade; interrupted/aborted upgrade; and incompatible schema. Check keys, indexes, representative records and counts before/after, not just whether Settings opens. Confirm semantic indexes, cached transcripts, and registry evidence survive. Model Cache Storage must remain untouched. No full reset is part of acceptance.
7. **Controlled device rollout.** Verify Mac Chrome against its existing data first after the isolated tests. Then test relevant desktop operations (storage report, semantic indexing/retrieval and reload, cached transcript save/export, model registry). Because the owner affects shared iPhone storage paths, identify and run a focused iPhone checklist after commit/publication: startup/Settings, Tiny self-test with persisted result, cached transcription, semantic indexing/reload, and relevant exports. Record exact build/device/browser and outcomes. Windows verification follows when the Alienware is available; do not report it as tested beforehand.
8. **Resume remaining runtime work.** Verify the blocked Settings target filter, review Search audio detection, and reconcile legacy reporting as separate changes. The larger registry project still needs its model-to-worker/evidence audit and baseline; database repair does not complete those stages.

## Preservation and rollout constraints

- No clear-storage instruction, database reset, or Rebuild Registry action to conceal the missing store.
- Existing transcript records, semantic data, registry evidence, and model assets must survive the repair.
- A restored older app build may be unable to open a newer database if it hardcodes version 4. Define a compatible rollback/forward-fix strategy before deployment; reverting JavaScript is not automatically a database downgrade.
- Test each independently deployable change and pause for the user's results. A schema transition may require a coordinated change across files; splitting its deployment into incompatible intermediate versions increases risk.
- Do not commit or publish without user instruction. Test evidence and remaining device checks are recorded in CURRENT_STATUS.md.

## Completion evidence

Retain the opener/consumer map, schema inventory, chosen version and upgrade rules, isolated test results, before/after preservation checks, blocked-tab behavior, device/build-specific acceptance results, and unresolved limitations. The repair is complete only when both existing incomplete and healthy databases work without data loss and every production database open uses the canonical owner.
